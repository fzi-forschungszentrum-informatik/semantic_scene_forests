# semantic_scene_forests_query

ROS 2 component that answers language queries against the current scene graph and object state.

## Task

- Cache the latest scene graph and managed objects.
- Expose action servers for object lookup and free-form LLM prompting.
- Fetch object visuals when a query needs image evidence.

## Runtime Interface

| Kind | Name | Type |
|---|---|---|
| Subscribe | `/scene_graph` | `semantic_scene_forests_msgs/msg/SceneGraph` |
| Subscribe | `managed_objects` | `semantic_scene_forests_object_msgs/msg/ManagedObjectArray` |
| Action server | `find_object` | `semantic_scene_forests_planning_msgs/action/FindObject` |
| Action server | `prompt_llm` | `semantic_scene_forests_planning_msgs/action/PromptLLM` |
| Service client | `get_object_visuals` | `semantic_scene_forests_object_msgs/srv/GetObjectVisuals` |

## Semantics and Limitations

- Queries require an authoritative managed-object array before they can answer; a confirmed
  empty array is a valid empty scene.
- A genuine `found:false` answer is SUCCEEDED with `success=false`/`id=-1`. Malformed model
  output, fabricated IDs, and results computed against stale membership are ABORTED with
  `success=false`/`id=-1`.
- Membership changes (epoch bump) invalidate in-flight query work: affected goals abort and
  are not retried automatically.
- Cancellation is cooperative. Synchronous HTTP calls cannot be force-canceled: stop
  checkpoints fire between agent steps, each call is bounded by its own timeout
  (`llm_connect_timeout_seconds`/`llm_request_timeout_seconds`), and there is no single
  overall deadline for all steps of a goal.
- During node teardown, in-flight goals are stopped cooperatively at the next tool
  boundary and need not receive a terminal result; there is no shutdown result-delivery
  guarantee.
- Known upstream limitation: SIGINT in the rclcpp_action goal-ACCEPT window can throw
  `Failed to accept new goal` out of the autogenerated component-container `main`.
- Concurrency note: the epoch/receipt gate and the current-active re-check run in separate
  lock windows; the first epoch check is the result's linearization point, not a guarantee
  of perfect future atomicity.
