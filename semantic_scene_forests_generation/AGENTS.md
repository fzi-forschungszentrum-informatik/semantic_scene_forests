# semantic_scene_forests_generation

C++23 ROS2 component that generates semantic scene graphs from detected objects using a two-phase VLM/LLM pipeline.

## Project Configuration

**IMPORTANT**: This is a monorepo. All project-wide configuration (code style, git conventions, graphify usage) is defined in the root [`AGENTS.md`](../AGENTS.md).

Refer to the root `AGENTS.md` for:
- C/C++ code formatting and linting
- Git commit conventions
- Graphify knowledge graph usage
- Context7 documentation lookup

## Architecture

Two CMake shared libraries:

| Target | Contents |
|---|---|
| `semantic_scene_forests_generation_component` | ROS2 component node + `IObjectTask` / `IGraphTask` plugin base classes |
| `semantic_scene_forests_generation_tasks` | Five default pluginlib task plugins |

A standalone executable (`semantic_scene_forests_generation_node`) is auto-generated by `rclcpp_components_register_node` — no `main.cpp` needed.

## ROS Interface

```
Sub   /managed_objects     semantic_scene_forests_msgs/ManagedObjectArray    QoS: keep_last(1), reliable, transient_local
Pub   /scene_graph         semantic_scene_forests_msgs/SceneGraph            QoS: same, 1 Hz timer
Srv   /get_object_visuals  semantic_scene_forests_object_msgs/GetObjectVisuals  (client, called during Phase 1)
Act   /update_scene_graph  semantic_scene_forests_msgs/UpdateSceneGraph      (server, Phase 1 or Phase 2)
```

## Plugin System

**Phase 1 plugins** implement `semantic_scene_forests_generation::IObjectTask` (`include/semantic_scene_forests_generation/task_interface.hpp`):
- Called once per managed object
- Receive a pre-populated chat history (system message + multimodal object-setup message)
- Call `chatTurn(client, history, prompt, logger)` from `src/tasks/task_utils.hpp`
- Write concept nodes and edges into the `SceneGraph`

**Phase 2 plugins** implement `semantic_scene_forests_generation::IGraphTask`:
- Called once per Phase 2 run
- Receive the full current graph and a pre-populated meta-setup history

### Adding a new task plugin

1. Create `src/tasks/my_task.hpp` + `src/tasks/my_task.cpp` inheriting from `IObjectTask` or `IGraphTask`
2. Add `PLUGINLIB_EXPORT_CLASS(...)` to `src/tasks/task_plugins.cpp`
3. Add an entry to `semantic_scene_forests_generation_plugins.xml`
4. Add the `.cpp` to `semantic_scene_forests_generation_tasks` in `CMakeLists.txt`
5. Add the plugin class name to `phase1_tasks` or `phase2_tasks` in the launch config / parameter overrides

## Prompt Templates

Jinja2 templates live in `resources/{instance,meta}/*.j2`. At runtime they are loaded from `prompt_dir` and keyed by relative path without extension (e.g., `"instance/single_attribute"`). Context variables are passed as `nlohmann::json` objects via `minja::Context::make(minja::Value(json_ctx))`.

## Update Execution

- **Goals are serialized**: the node accepts one `/update_scene_graph` goal at a time on an owned `std::jthread` worker; admission is reject-while-busy, and a goal caught in teardown receives no terminal result.
- **Cooperative stopping**: the worker checks a stop token at existing checkpoints (before external calls, per task, and before commit). Teardown requests stop, lets the current blocking call finish, then joins; waiting is bounded by the per-call timeouts, not by a whole-goal shutdown deadline.
- **Graph snapshots isolate long-running work**: LLM tasks operate on a private graph snapshot. The live graph mutex is held only to clone or commit a graph, so publishing and diagnostics remain responsive during inference.
- **Bounded external calls**: LLM connection/request timeouts and object-visuals request timeouts are parameters. Cancellation is checked between external calls; an in-flight HTTP request cannot be force-cancelled but is bounded by the request timeout.

```bash
colcon build --packages-select semantic_scene_forests_generation
```

## graphify

**IMPORTANT**: Use the graphify knowledge graph in the **monorepo root** (`graphify-out/`), not in this package subdirectory.

When the user types `/graphify`, invoke the `skill` tool with `skill: "graphify"` before doing anything else.

Rules:
- For codebase questions, first run `graphify query "<question>"` when graphify-out/graph.json exists. Use `graphify path "<A>" "<B>"` for relationships and `graphify explain "<concept>"` for focused concepts. These return a scoped subgraph, usually much smaller than GRAPH_REPORT.md or raw grep output.
- Dirty graphify-out/ files are expected after hooks or incremental updates; dirty graph files are not a reason to skip graphify. Only skip graphify if the task is about stale or incorrect graph output, or the user explicitly says not to use it.
- If graphify-out/wiki/index.md exists, use it for broad navigation instead of raw source browsing.
- Read graphify-out/GRAPH_REPORT.md only for broad architecture review or when query/path/explain do not surface enough context.
- After modifying code, run `graphify update .` to keep the graph current (AST-only, no API cost).
